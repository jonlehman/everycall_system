# Manual Sales introduction email

Status: Owner requested November 9, 2026. Implementation and migration require independent review before release. No live send is part of fixture verification.

The Sales Close tab opens an editable plain-text introduction addressed to the selected active company contact. The supplied Everycall introduction, public demo link and literal Ram signature are the initial draft. Sending occurs only after the rep presses Send. The server uses the existing configured Resend/Mailtrap sender and sets Reply-To to the authenticated account email. No inbox integration, campaign, call creation, outcome, booking, checkout, payment or knowledge operation is added.

POST `/api/v1/admin/sales/prospects/:id/intro-email/draft` accepts `{contactId,salesCallId?}` and returns `{ok:true,draft:{draftToken,contactId,recipient,replyTo,subject,text,expectedRowVersion,requiresEmailPermissionConfirmation}}`. The opaque, one-hour draft binds the actor, company version, selected contact and hashes of the actual recipient and account Reply-To. A supplied call must belong to that rep/company and its frozen contact/email must still match. Legacy calls without a contact snapshot cannot provide a send context; the rep may open the company independently.

POST `/api/v1/admin/sales/prospects/:id/intro-email` accepts only `{draftToken,subject,text,confirmedEmailPermission?}` with a stable `Idempotency-Key`. Recipient, sender, Reply-To, call, CC/BCC and HTML cannot be supplied in this request. Subject is 1–200 characters without control characters or line breaks; plain-text body is 1–12,000 characters. A selected nondefault contact never inherits the legacy default contact's email permission. When permission is absent for this exact default/email identity, the rep must explicitly confirm the selected contact agreed to this particular email. That confirmation is stored only with the delivery and never grants company or campaign permission. It cannot override email suppression, permanent DNC, removal or phone testing.

`0060_sales_intro_email.sql` adds a dedicated delivery ledger because checkout/signup/booking records have different identities and effects, while generic idempotency receipts expire and cannot preserve uncertain external attempts. Draft identity is immutable. Send commits a `sending` reservation and message digest before dispatch. A second transaction reacquires config, actor and company locks, validates current context, and holds them through a provider attempt bounded to 15 seconds. Success records `sent`; provider failure, timeout or post-send commit uncertainty leaves `uncertain` or `sending`. No scheduler retries either state. An unresolved attempt fences every other draft/key for that company. The same successful draft/request replays its receipt; changing the key or message cannot resend that draft.

The ledger stores hashes rather than raw recipient/Reply-To/message content. Audit records include delivery, actor, company/contact/call IDs, status and explicit permission confirmation only. Existing mail callers omit the new optional Reply-To argument and keep their current behavior. Unresolved-delivery database triggers block selected identity/assignment changes and phone-mode transitions while allowing opt-out/permission revocation and ordinary call wrap-up. A missing ledger fails only this new endpoint with an actionable 503; unrelated runtime readiness is unchanged.

Internal operator maintenance can reconcile an unresolved attempt after at least 15 minutes using `reconcileSalesIntroEmailDelivery`, which verifies an administrator role, locks the current mode/actor/company/delivery, and atomically stores a non-PII evidence reference with an audit. A positively verified provider send resolves to `sent`; positively verified non-delivery resolves to `canceled`. Missing dashboard/search results are not proof of non-delivery. This function has no HTTP endpoint, never calls a provider or resends, preserves the immutable recipient/request, and requires a transaction-local reconciliation context for an `uncertain` transition. Sales users cannot override the fence.

Both draft/reservation and dispatch revalidate the trusted authenticated session ID, user, role, namespace and expiry from the database. Session and operator-active rows stay locked through dispatch alongside the account/company; logout, password/session revocation, expiry or disabling between reservation and dispatch cancels the attempt before any provider call. Expiry is checked again after dispatch locks are acquired. The SQL composite foreign key independently prevents a delivery from referencing another company's contact.
