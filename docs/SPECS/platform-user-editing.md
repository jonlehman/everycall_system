# Platform user editing

Owner-requested existing-user editing in `/admin/users` (2026-11-05).

- **PUE-01 — Stable identity:** Every existing row exposes Edit and its database user ID. The form prefills name (`admin_users.username`), email and role. PATCH `/api/v1/admin/users` targets the existing `id`; it never inserts a replacement account or changes the ID. Cancel discards the draft. Create / Reset retains its separate POST flow and existing email-based reset behavior.
- **PUE-02 — Validation:** Name and normalized email are required and distinct from other platform accounts (case-insensitive comparison). Roles remain `admin`, `super_admin`, `sales`; existing admins and super admins retain equal user-management access. Invalid fields return 400, missing IDs 404, duplicate names/emails 409. Only ID and the four editable fields are accepted; database errors do not expose their details.
- **PUE-03 — Credentials:** Blank or omitted edit password preserves the hash. A supplied password requires at least eight characters and at most 72 UTF-8 bytes (bcrypt's effective limit), and is bcrypt-hashed at cost 10. Email, role or password changes revoke both admin and Sales sessions and platform reset tokens bound to the old account email; unrelated tenant tokens sharing a numeric ID remain intact. Name-only edits retain sessions. No password/hash/session identifier enters the user response or mutation audit.
- **PUE-04 — Atomic authorization:** Account writes serialize on one transaction advisory lock, then recheck the actual current admin user and an unexpired, tenant-free admin session inside the transaction. Last-admin demotion is rejected unless another admin/super admin has a usable email and password hash. POST resets share these protections. The update, operator provisioning, session/token revocation and audit commit together; audit failure rolls back all changes.
- **PUE-05 — Related data:** Prospect assignments, call history and all account foreign keys remain bound to the same ID. Sales conversion provisions missing active operator settings. Existing operator settings are untouched, including deliberately disabled status, credential ID, caller ID and display name. Operator display name is independently configured; even a prior default-derived display name stays unchanged and can be edited in Sales Settings.
- **PUE-06 — Races and self-edit:** Login session issuance locks the account and compares the email, role and password hash to the credential snapshot verified by login. Stale logins cannot resurrect access after an edit. Platform password reset issuance validates the account snapshot under the mutation lock; redemption revalidates its token there and commits password/session/token/audit changes together. Historical unscoped tokens that match both a platform and tenant account ID/email are rejected rather than guessing the principal. Tenant-scoped resets keep their existing behavior. A self-edit that revokes sessions clears both cookies and shows a saved confirmation with the appropriate admin or Sales sign-in link, without attempting to reload protected data.

Implementation: `pages/api/v1/admin/users.js`, `pages/api/_lib/platformUsers.js`, `pages/api/_lib/auth.js`, admin/Sales login, reset issuance and redemption paths, `app/admin/users/page.jsx`.

Regression: `scripts/validate-admin-user-edit.mjs` covers PUE-01–06 with a disposable database; native PostgreSQL mode verifies genuinely overlapping account demotions, revoked queued actors, login credential changes and revoked reset tokens. `scripts/test-admin-user-edit-browser.mjs` verifies identity/prefill, cancel, optional password, role changes, conflict recovery, in-flight disabling and self-edit sign-in. Existing Sales auth and assignment suites cover workspace separation and unchanged ownership behavior. No schema migration or live-account/provider operation is needed.
